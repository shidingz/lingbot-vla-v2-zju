02做了哪些修改，为什么能加速

Profiling 指向 MoE 路径：逐专家小算子、主机同步和排序回退，使 NPU 计算被频繁打断。优化将专家计算成组提交，并把分组准备留在设备上。

原路径：逐专家执行

专家计数回 CPU → Python 循环
多个小矩阵乘 + 整数排序回退

→
新路径：NPU 成组执行

设备端分组 → Grouped GEMM
原生前向 + 完整的一阶梯度

1

每个投影用 grouped GEMM，一次处理多个专家

gate / up / down 三个投影分别调用 npu_grouped_matmul，替换 Python 逐专家矩阵乘，减少小算子与调度开销。

2

补齐训练反向，权重梯度使用 FP32 累加

当前 torch_npu 2.6 的该原生算子缺少训练梯度支持，因此显式实现输入与权重梯度；空专家梯度归零，兼容 FSDP2 和检查点重计算。

3

移除计数回传与整数排序的 AICPU 回退

token 计数及累加保留在 NPU，移除 .tolist() 同步；专家 ID 转为可精确表示的 FP32 后稳定排序，保持原路由顺序。

4

接入默认训练脚本，保留一键切回原实现

NPU 非专家并行路径默认选择 GMM；保留专家权重名称、形状及路由器 FP32 计算，提供环境变量切换。

03对照实验保持了什么条件

同一训练配置：预训练权重、随机种子、数据及顺序一致；8 卡 × 每卡 12，梯度累积 1；保留 Muon、原 FP32/BF16 策略、teacher 与梯度检查点。

同一计时口径：先 torch、后 GMM，各跑 40 步，学习率调度总步数仍为 5717；比较第 13–29 步共 17 次更新，排除初始化、profiler 预热 / 采集 / 导出及后续等待。短跑关闭检查点保存与 OBS 上传。
